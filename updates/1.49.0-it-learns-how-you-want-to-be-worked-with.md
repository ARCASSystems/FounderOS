# v1.49.0 - it learns how you want to be worked with, and the team keeps its own record

Two changes, one idea behind both. The chat app you came from already has memory, so "it remembers you" is not a reason to install a folder of files. What a folder can do that a memory cannot is land the thing somewhere that gets read **before** the OS acts, in a file you can open, argue with, and delete a line from.

## What changed

- **`core/working-preferences.md` is new, and it ships empty.** It holds how you want to be worked with, not what you know: decide for me or give me options, show the working or just answer, what never to ask twice, the shape of a normal answer, what "done" means to you, and anything the OS proposed once and got told off for. It is read before output, exactly where `core/voice-profile.yml` is read before anything is written.

- **Your corrections are the source, not a settings screen.** Say "too long", "you asked me that already", "just pick one", and two things happen in order: the reply you are reading gets fixed, then one line at the end asks whether to stop doing it for good. On your yes it becomes a row with today's date and your exact sentence next to it. Every row carries its evidence, because a preference with no source is somebody's guess about you, and guesses are what the file exists to replace.

- **Nothing lands without your yes.** Sessions propose, only you promote. `/founder-os:dream` gained a fifth target class so a preference buried in a rant gets found, but `/dream` runs unattended, so its candidates go to a **Proposed** table and wait. Proposed rows never gate output. The session brief counts them, the morning loop asks about them one at a time, and a no deletes the row rather than parking it.

- **Four surfaces read it.** The bootloader (every session), `brain/.snapshot.md` (which nine output-producing skills already read), `founder-next-move`, and `morning-loop`. The morning loop reads it as a gate on its own questions: a loop whose whole job is to stop asking questions you already answered is the last place that should ignore a preference. Missing file means all four carry on as before.

- **Your five roles now write their own run records.** `scripts/agent_runs.py` appends one line per run to `brain/agent-runs.jsonl`: what triggered it, what it read, what it produced, how it ended, what it could not do. `python scripts/employee_verdict.py render` shows runs beside verdicts, so you can see a seat ran fourteen times and you graded three. `drift` now reports an `active` row the run log has never seen.

- **`refused` is not a failure.** A propose-only job that declined because its charter said no is the charter working, and a log that could not say so would file every honest refusal under failed.

## Why it matters to you

**If you have ever given the same correction twice:** that is the thing this release exists to stop, and it is the test to hold it to. Give a correction, say yes when asked, and check `core/working-preferences.md` - your sentence should be in it with today's date. If you find yourself giving that same correction a week later, the loop is broken and it is worth saying so plainly: either the row was never written or nothing read it. Both are bugs in the OS.

**If you would rather the OS did not learn anything about you:** delete `core/working-preferences.md` and nothing changes. Every read point treats a missing file as normal. There is no hidden store, and nothing about your preferences leaves your machine.

**If you run any of the five starter roles:** your org chart starts telling the truth about what has actually run instead of what you happened to notice. This is worth most on the runs you were not watching, which is where a quiet mistake lives.

**Two limits, stated rather than implied.** A run line says a run happened; it says nothing about whether the output was any good, which is still your one-word verdict. And a job that does not record cannot be told apart from a job that did not run, which is why the drift finding names both rather than picking one.

## Integration protocol

1. **Take the system-layer files.** Scripts, skills, commands, and the hook are engine; none of them writes into your data folders on update.
2. **Copy `templates/working-preferences.md` to `core/working-preferences.md`.** Do not personalize it and do not seed a row. It is meant to be empty until you correct something.
3. **If you edited `CLAUDE.md`,** take the two new bits by hand rather than overwriting: the `core/working-preferences.md` line in the boot list, and capture Shape 5. Everything else in that file is unchanged.
4. **If you edited `roles/employees.yaml`,** update `run_record_source` on each row you kept to `brain/agent-runs.jsonl, the lines whose seat is <id>`, and add `Bash(python scripts/agent_runs.py:*)` to that row's `tools`. Then run `python scripts/employee_verdict.py charters` - it names any row whose grant and skill have drifted apart.
5. **Prove the read point in one command.** `python scripts/brain-snapshot.py --write`, then open `brain/.snapshot.md`. With an empty preferences file there is no preferences block, which is correct. Add one Active row by hand, run it again, and the block is there. That is the chain the output skills read.

## No Claude Code? The by-hand path

**Create one file called `working-preferences.md` in your `core/` folder, with one heading called Active and one called Proposed, and each time you catch yourself correcting your assistant the same way twice, write the correction under Active with today's date and the words you actually said.** Then tell whatever assistant you use to read that file before it answers you. The rest of this release is plumbing that does those two steps for you. The habit is the whole feature.
