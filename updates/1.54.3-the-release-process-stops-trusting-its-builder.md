# v1.54.3 - the release process stops trusting its builder

Three releases in a row were corrected by outside review, and the post-mortem found the same three causes each time: the person who builds a change tests it from the same wrong idea, a fix lands on the one file where the problem was noticed while its twins ship untouched, and the riskiest code had the least coverage because it looked small. None of those are effort problems. They are structure problems, so this release changes the structure and writes it where you can read it.

## What changed

- **The release standard is now a shipped page.** `rules/release-verification.md` states the four gates every release must pass from now on: a second context that did not build the change tries to break its claims before the push, every promise you can read in an update pack carries a test that tried to make it false or an honest unverified label, a fix for a reviewed defect must show the whole repo was searched for the same pattern, and code that handles secrets, sends, deletes, or reports safety carries tests by mechanical rule rather than judgment. The page also says what good looks like honestly: not zero findings - a review that finds nothing is usually shallow - but falling severity and no defect class ever found twice.

- **The commit rules point at it.** The release-commit section of `rules/commit-naming.md` now opens with the gate: naming a release well matters less than the release deserving its name.

- **The coverage floor found real debt on day one.** The mechanical check flagged five scripts with no test naming them, among them the session-undo net, the capability-page builder, and the provisional-facts ledger - the exact machinery whose honesty the OS leans on. They are recorded as named, dated debt on a list frozen to its founding day: an entry that gains coverage must leave, and no new entry can ever be added, so the list cannot rot into a permanent exemption sheet. The check itself runs in the maintainer's suite upstream of every release rather than shipping in this repo. That is the honest state of the maintainer's tree today, written down instead of discovered later.

## Why it matters to you

**If you follow this project's releases:** the patch-after-patch rhythm of the last week is the thing this release ends. The same scrutiny that produced those patches now runs before a release ships, not after you have already pulled it.

**If you evaluate whether to trust this OS at all:** the standard it holds itself to is now a file in your install, checkable like everything else - the same move as the security page. A project telling you its own failure history and what it changed is a better signal than one showing you an unbroken green wall.

**If you contribute:** the four gates apply to your change too, and the page explains why in terms of this repo's own shipped mistakes, not policy language.

## Integration protocol

1. Both files arrive with the update itself. No action needed.
2. Nothing in your own files is touched, no script changes, no behaviour changes. This release changes how future releases are made.

## No Claude Code? The by-hand path

Nothing to copy. The one idea worth taking is the rule itself, because it applies to any work you check with AI: the person or model that made a thing cannot be the only one who checks it, and "review this" produces agreement while "try to break this specific claim" produces findings. If you use AI on documents that matter, make the second pass a different session with none of the first one's context, and ask it to refute, not to review.
